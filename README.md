# Echo Chamber

A personal streaming site for the music in the parent folder, live at https://myechochamber.vercel.app. Next.js on Vercel, catalog in Supabase, audio in Cloudflare R2.

```
Browser ──▶ Vercel (Next.js)  ── pages, search, API
   │            │
   │            └──▶ Supabase Postgres ── artists / albums / tracks / plays / playlists
   │
   └──(302 signed URL)──▶ Cloudflare R2 ── the MP3s (free egress)
```

- **Album art** is generated by the ingest script into `public/covers/` and served as static files by Vercel.
- **Audio** never passes through Vercel. `/api/stream/<id>` redirects to a signed R2 URL that expires after a few hours, so the bucket itself stays private.
- **Accounts are optional.** Guests can listen, search and open shared playlist links. Signing up (username + 6-digit PIN) adds playlists, sharing and device sync. The site is marked `noindex` so search engines skip it.
- **Supabase** tables have RLS enabled with no public policies. Only the server (using the secret key) can read them.

## Accounts, sharing and device sync

**Accounts.** Anyone can sign up with a username (3–20 letters, numbers, `_` or `.`) and a 6-digit PIN. PINs are stored as scrypt hashes, and an account locks for 15 minutes after 5 wrong PINs. Sessions are an httpOnly cookie (the database stores only a SHA-256 of it) and last a year. The Account page lists your signed-in devices so you can sign any of them out, and changing your PIN signs out all the others. Admins get an `/admin` page where they can reset a PIN (a new one is shown once), unlock, promote or delete accounts. To make someone an admin the first time, run `update users set is_admin = true where username = '…';` in the Supabase SQL editor.

**Playlists.** Each playlist has an owner and is Private or Public; you choose when you create it. Only the owner can manage it, and there are three ways to share it:
- **People:** pick users from a list and give each *Can view* or *Can edit*. Editors can add, remove and reorder songs; only the owner can rename, share, change the cover or delete.
- **Link:** turn on a share link that anyone can play, even without an account. Turning it off breaks old links.
- **Public:** public playlists are listed on the owner's profile (`/u/<username>`). Anyone signed in can save them to their library or make their own editable copy.

Owners can upload a custom cover. It's resized to a 600px WebP, stored in R2 under `playlist-covers/`, and served through a signed redirect.

**Device sync (Spotify Connect style).** Each signed-in browser tab joins a Supabase Realtime channel named by the user's secret `sync_key`. Presence tracks which devices are online.
- **One device plays at a time.** It broadcasts what's playing, and your other devices show it and act as remotes: play/pause, skip, seek, volume, queue. Tapping a song on a remote plays it on the active device.
- **The speaker button** lists your online devices. Choosing one moves playback there, continuing from the same position.
- **Resuming.** The active device saves its queue and position to `playback_state` about every 20 seconds and whenever you pause or change track. A device that opens with nothing playing picks up from there, paused.
- **The browser's publishable key** is only used for Realtime. Every table is RLS-locked, so it can't read data, and the channel name is an unguessable per-user UUID. Resetting a user's PIN from the admin page rotates it.
- **Traffic stays small.** The playing device only sends a heartbeat every 10 seconds, and only while another of your devices is online. That keeps it well inside Supabase's free Realtime allowance (200 concurrent connections, 2 million messages a month).
- **Browser limits.** Browsers only let audio start from a tap. Moving playback to the device you're holding always works. Pushing it to another device works if that device has played something since it was opened, which is the usual case. Otherwise it shows the song paused, ready to tap play.

## Costs and free tiers

The whole stack runs on free plans. Cloudflare is the only service with a card on file, and storage over 10 GB is the only thing there that costs money.

### What each service holds

| | Cloudflare R2 | Supabase | Vercel |
|---|---|---|---|
| **Stores** | The MP3 files (939 tracks) and custom playlist covers | Catalog, accounts, playlists and sharing, play history, resume state, realtime device sync | Website code and album art |
| **Size** | ~4.65 GB | Under 1 MB | ~11 MB of covers |
| **Free limit that matters** | 10 GB storage; streaming free | 500 MB database, 5 GB egress/month | 100 GB bandwidth/month |
| **Card on file** | Yes (required to turn on R2) | No | No |
| **If a limit is exceeded** | Billed (~$0.015 per extra GB-month) | Warning, then restricted; never billed | Paused; never billed |

### What happens when a song plays

1. Vercel renders the page using the catalog from Supabase.
2. Pressing play hits `/api/stream/<id>` on Vercel, which redirects to a temporary signed R2 URL.
3. The audio streams directly from R2 to the browser, never through Vercel or Supabase. That's one R2 read (Class B), and the bandwidth is free.
4. After 30 seconds of listening, a play is logged in Supabase for "Most played".

### Cloudflare: only R2 is used

This project uses **one Cloudflare product, R2 Object Storage**: a single bucket (`tims-music`, Standard storage, public access off) and a single API token scoped to it. Workers, D1, KV, Durable Objects and Pages are not used, so their limits on the [Workers plans page](https://dash.cloudflare.com/?to=/:account/workers/plans) (for example "5 GB" for D1 and Durable Objects) don't apply.

| R2 metric (per month) | Free | Used by | Price over the free amount |
|---|---|---|---|
| Storage | 10 GB-month | The MP3s | $0.015 / GB-month |
| Class A operations (writes) | 1 million | Uploads from `npm run ingest` | $4.50 / million |
| Class B operations (reads) | 10 million | Each play or seek, plus ingest's existence checks | $0.36 / million |
| Egress (streaming) | Unlimited | Audio sent to listeners | Free |

Sizes here use decimal GB (1 GB = 1,000,000,000 bytes), the same unit as the Cloudflare dashboard and macOS Finder. Tools like `du` use binary units, which is why they report the same library as ~4.33 GB. The ingest script refuses to upload more than 9 GB unless you pass `--allow-paid`, and `--prune` deletes removed tracks from R2 (deletes are free) so they stop counting toward storage.

**Sources.** Everything in the R2 table comes from Cloudflare's [R2 pricing page](https://developers.cloudflare.com/r2/pricing/):
- The **Free tier** table gives the free amounts.
- The **R2 pricing** table gives the Standard storage prices.
- The **Egress** row in both tables says Free.
- The **Caution** note says the free tier only covers Standard storage.
- The **Class A / Class B operations** sections list which operations count as each (PutObject counts as Class A; GetObject and HeadObject count as Class B).
- The FAQ says requests rejected as unauthorized aren't billed.

Supabase's free-plan limits are on its [pricing page](https://supabase.com/pricing). A daily Vercel cron (`vercel.json` calling `/api/keepalive`) keeps the free project from pausing after 7 days of inactivity.

### Checking usage in the Cloudflare dashboard

These links open the matching page in whichever Cloudflare account you're logged into:

- [R2 overview](https://dash.cloudflare.com/?to=/:account/r2/overview): current bill, Class A/B operation counts, total storage. There's also an **Add Budget Alert** button for email alerts if charges ever appear.
- [The `tims-music` bucket](https://dash.cloudflare.com/?to=/:account/r2/default/buckets/tims-music): storage class, public access, stored files.
- [R2 API tokens](https://dash.cloudflare.com/?to=/:account/r2/api-tokens): the token the app and ingest script use.
- [Billing](https://dash.cloudflare.com/?to=/:account/billing): payment method and invoices.

The dashboard's storage total updates with a delay. Right after an upload it can show 0 B for a few hours even though the files are there.

## Setting up from scratch

1. Create a Supabase project and run `supabase/schema.sql` in its SQL editor.
2. Create an R2 bucket (Standard storage) and an API token with Object Read & Write on it.
3. Fill in `.env.local` (see below) and run `npm install`.
4. `npm run ingest` uploads the music, writes the catalog, and generates `public/covers/`. The album art isn't in this repo because it's copyrighted and derived from the local library.
5. Deploy with `vercel --prod` from this folder, so the generated covers go with the deploy.

## Environment

Copy `.env.example` to `.env.local` and fill it in. Add the same variables in Vercel under Project Settings → Environment Variables.

| Variable | Where to get it |
|---|---|
| `SUPABASE_URL` | Already filled in |
| `SUPABASE_SECRET_KEY` | Supabase → Project Settings → API Keys → Secret keys (`sb_secret_…`) |
| `R2_ACCOUNT_ID` | Cloudflare dashboard → R2 → Account ID (right sidebar) |
| `R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY` | R2 → Manage API tokens → Create API token → Object Read & Write, scoped to the bucket |
| `R2_BUCKET` | The bucket name (default `tims-music`) |
| `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Supabase → Project Settings → API Keys → Publishable key. Used in the browser for realtime device sync only |

## Adding or changing music

1. Put new albums in the parent folder as `Artist/(Year) - Album - Artist/…mp3`. `Disc N` subfolders work too.
2. `npm run ingest`. Only new or changed files get uploaded, because files are keyed by content hash.
   - `-- --dry-run` scans and builds covers without uploading anything
   - `-- --prune` removes database entries for files you deleted
   - `-- --force-covers` regenerates all artwork
   - The script refuses to upload past 9 GB so R2 stays on the free tier. `-- --allow-paid` overrides that.
3. Redeploy (`vercel --prod`) so new cover art goes live.
